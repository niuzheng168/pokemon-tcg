# 效果单元逐条复核（双模型一致 + Claude 复核）

2026-10-22。用户决定：两个模型翻译一致、内核检查通过，但没有独立模板证书覆盖的效果单元，
**由 Claude 逐条语义复核后准入**；只接受判为「正确」的，错误和存疑的退回队列；
证书里单独标明这一来源，与模板证书、已审核程序复用和机制证书分开。

## 准入条件

一个效果单元以 `consensus-review` 族进入 `catalog/zh-CN/V20261019/library/machine/effects.json`，须同时满足：

1. 没有任何窄模板、已审核程序或机制证书能认证它（能认证的走原来的族，见 `tests/effect-review-certificates.test.mjs`）。
2. 两个模型（astra、sol）的完整程序规范化后**逐字段相同**（`canonicalEffectResult`，比 Python 侧的一致性比较更严格）。
3. 内核效果检查通过（`scripts/effect-validate.mjs`）。
4. 不含 `cn.orElse@1` 兜底，也不含 `needsRuling` 占位。卡面让玩家选择时不能改成固定顺序，未决裁定不算已复核的行为。
5. 已提交的复核账本 `catalog/zh-CN/V20261019/library/machine/effect-reviews.json` 里，这个单元的结论是 `correct`，
   而且记录的 `programSha256` 等于准入程序的规范化摘要。程序有任何改动，摘要就对不上，不能准入。
6. 不属于下面「一致性检查」列出的、处理器无法准确表达的写法。

`scripts/build-machine-catalog.mjs` 在干净克隆里重新核对第 3–6 条（账本和证书都已提交，不需要模型缓存）；
第 1–2 条在本机生成证书时核对（`scripts/build-effect-candidates.mjs`）。

## 复核过程

- 对象：1,568 个「双模型一致且内核有效、尚未认证」的单元，先排除 17 个含 `needsRuling`、5 个含 `cn.orElse@1` 的，
  剩 **1,546** 个，按解锁印刷数排序，分 35 批，每批约 45 个。
- 每批另外混入 2 个**隐藏诱饵**：取别批单元的程序，改动一个数字、一方、状态、区域、正反面或删掉一个效果，
  换一个看不出来源的 uid。诱饵答案放在复核目录之外，复核者看不到。
- 复核者是 Claude 子 agent（每批一个，互相独立），先读 `.data/effect-translation/handler-reference.md`，
  必要时查 `public/rules/` 的实现，逐条判断程序行为是否与卡面**完全一致**，给出 `correct` / `wrong` / `unsure` 和理由。
  提示词全文见文末。
- 生成账本：`node scripts/build-effect-reviews.mjs --key <诱饵答案> --publish`。诱饵只计分，不进账本。

## 结果

| 项目 | 数量 |
| --- | ---: |
| 复核单元 | 1,546 |
| 判为正确 | 1,523 |
| 复核者判错／存疑 | 11／2 |
| 一致性检查退回 | 10 |
| 准入（`consensus-review`） | 1,521 |
| 诱饵：放入／识别 | 70／67 |

没识别的 3 个诱饵，都是把数量 1 的 `exact` 改成 `upTo`（或反过来）。引擎对公开区和牌库检索的「1张」和「最多1张」
选择范围相同，行为没有变化，所以这 3 个改动不构成错误。改变了行为的诱饵全部识别。
另有 2 个单元两个模型的程序只在 Python 宽松比较下一致，严格比较不一致，因此即使判为正确也不准入。

复核者判错的 11 个真实单元包括：「若希望」检索被写成必须拿取、卡名标签写成中文（「连击」而非 `Rapid Strike`）、
弃牌区附着能量的固定张数、合计张数等。它们和判为存疑的 2 个一起留在待认证队列。

## 一致性检查

不同批次的复核者对同一类写法偶尔判法不同。凡是有一位复核者查实了处理器表达不了的写法，
就对所有单元统一执行（`scripts/effect-review-certificates.mjs` 的 `inexpressible`），不论该批复核者怎么判：

- **弃牌区附着的固定张数**：`attachDiscard` 的张数只是上限，公开区最少 1 张。卡面「弃牌区中的2张…附着」没有「最多」时，
  玩家可以只附 1 张，与卡面不符。
- **「若希望」的任意卡检索**：牌库里按「任意卡」检索时，`upTo`/`exact` 至少要拿 1 张，不能放弃。
- **不指名、不限阶段地放于备战区**：卡面只写「宝可梦」「【龙】宝可梦」时，能否放上非基础宝可梦需要有规则出处，暂不准入。
  指名卡（如「脱壳忍者」）和写明阶段的不受影响。
- **卡名标签写成中文**：内核的标签是 `Rapid Strike`、`V` 等目录写法，中文标签匹配不到任何宝可梦。
- **按特性名的例外**：「（除「X」外）」按特性名排除；`exceptAbilityIds` 只排除本定义的那一份，
  其他印刷的同名特性仍会被消除。

## 文件

- `scripts/effect-review-certificates.mjs`：族名、账本校验、程序摘要、准入判断、一致性检查。
- `scripts/build-effect-reviews.mjs`：从复核结果生成账本（本机，需要复核目录和诱饵答案）。
- `catalog/zh-CN/V20261019/library/machine/effect-reviews.json`：已提交的账本，包含全部 1,546 条结论（含判错、存疑的理由）、
  诱饵计分和复核日期。
- `tests/effect-review-certificates.test.mjs`：准入规则的正反例，以及已提交证书与账本的一致性。

## 复核提示词

```text
你是宝可梦集换式卡牌（简体中文官方规则 CN/V20261019）规则引擎的效果审核员。任务：逐项审核一批「卡面效果文字 → 引擎效果程序」的翻译是否语义完全正确。

工作目录：/home/zhn/pokemon-tcg-cn（只读，除了写下面指定的结果文件，不要修改任何文件）。

输入：.data/effect-review/batches/batch-NN.json —— JSON 数组，每项是一个效果单元：
- uid、kind（attack 招式 / ability 特性 / trainer 训练家卡 / energy 特殊能量）
- card（卡名、种类、阶段、HP、训练家类别）、attack（招式名、费用、印刷伤害栏，如 "120"、"30+"、"20×"，空串表示无伤害）、ability（特性名）
- text：卡面印的完整效果文字（简体中文）
- program：翻译出的引擎效果程序（`effects` 为 [key, handlerId, parameters] 列表；特性另有 mode/usage/trigger/condition；特殊能量另有 baseUnits；训练家另有 playCosts/condition）。占位符：DEF 表示本卡定义 ID，DEF:a 是本招式，DEF:b 是本特性，NAME:<名字> 是卡名键，CARD_EVIDENCE 是证据。
批次里混有少量故意改错的程序，用来检验审核灵敏度；每项都要独立、认真核对，不要假设大部分都对。

参考资料（必须先读）：
- .data/effect-translation/handler-reference.md：所有 handler 的参数含义、放置位置、组合方式和限制（§1–§5）。这是判断程序语义的依据。
- 需要时可以读 public/rules/handlers.js 及 public/rules/ 下相关实现，确认某个参数的确切含义（例如 quantity 的 exact 和 upTo、shuffleAfter、target、scope、coin 的含义）。只在必要时查，带回结论即可。

逐项判断：程序执行的效果是否与卡面文字**完全一致**——没有多出、没有遗漏、没有改动任何条款。重点核对：
- 数量与「最多」「任意数量」「全部」的区别；对象是自己还是对手、战斗宝可梦还是备战宝可梦还是全部；
- 区域（手牌、牌库、弃牌区、牌库上方/下方）；是否给对手看、是否重洗牌库；
- 特殊状态种类；硬币正反面各自的结果；伤害数值、「+」「×」公式的基数和倍数；
- 持续时间（这个回合、下一个对手的回合）；可选（「可以」「可选」「若希望」）与强制；条件（「如果……的话」）是否被保留；
- 由谁选择（自己还是对手）；卡面让玩家选择时，程序不能改成自动兜底（orElse）或固定顺序；
- 特性的使用时机、次数、发动条件；能量的属性和个数/张数。
同一个卡面意思有多种等价写法时，只要引擎行为相同就算正确。不要因为风格或键名不同判错。

verdict 取值：
- "correct"：行为与卡面完全一致；
- "wrong"：有任何可指出的差异（写出具体是哪个条款、程序怎么写的、应该怎样）；
- "unsure"：确实无法从参考资料判断（写出原因）。

输出：写 UTF-8 JSON 文件 .data/effect-review/results/result-NN.json，格式：
[{"uid": "<原样>", "verdict": "correct|wrong|unsure", "reason": "简短中文说明（correct 可留空）"}]
每一项都要有结果，uid 原样照抄。最后回复不超过 10 行的摘要：项数、三种 verdict 的数量、wrong 中最常见的几类问题。不要在回复里贴整份 JSON。
```

## 第二轮（2026-10-22，第 3 轮翻译之后）

- 对象：第 3 轮翻译后新出现的「双模型一致、内核有效、没有模板证书、复核为正确即可准入、且这份程序还没复核过」的单元，
  共 **1,852** 个，分 42 批（batch-36 至 batch-77），每批另混 2 个诱饵。批次脚本 `.data/analysis/review_batches_r2.mjs`，
  提示词同上（`.data/effect-review/PROMPT.md`）。
- 结果：判为正确 1,830，判错 16，存疑 6；诱饵 84 个识别 81 个（漏掉的 3 个同为数量 1 的 `exact`/`upTo` 互换，行为相同）。
- 判错和存疑的 22 个里有 15 个是同一个原因：卡文来源漏了「[对战中，己方的GX招式／VSTAR力量只能使用1次。]」，
  两个模型因此都没写 `specialRule`，程序会允许每回合使用。复核者对照卡图读数指出了这一点。处理见 STATUS §44。
- 账本改为同一 uid 以最后一次复核为准（程序在后续翻译轮次中变化时重新复核）；`build-effect-reviews.mjs` 按批次编号顺序读。
