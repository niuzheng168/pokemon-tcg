## 1. 不可混用的身份

| 身份 | 本版设计 |
| --- | --- |
| 规则地区 | `CN`；不是界面 locale |
| 卡牌发行语言 | `zh-Hans`；图片文字或转换后的展示文字不能证明发行语言 |
| 本项目规则版本 | `V20261019`；不是官方文档的版本号 |
| 官方文档 | 每份文档独立记录版本、章节、页序、读取证据和可取得的字节哈希 |
| 卡池赛制 | 独立、带日期的赛制配置；不能用 `modern` 替代 |
| 卡牌规则定义 | `definitionId`，绑定明确地区和规则版本 |
| 实体印刷身份 | `printingId`、语言、商品编号、完整卡号；不从文件名或同名猜测 |
| 对战实例 | 每张卡独立 `instanceId`，每个场上宝可梦独立 `pokemonId` |

官方文档更新不能原地改变旧对局。新增规则版本需要新的来源审查、
规则差异和测试；存档、重放和待完成选择必须继续绑定原版。

## 2. 规范优先级

1. 适用的简中官方更新、勘误与具体卡牌特例。
2. 简中官方进阶指南与基础玩法。
3. 相应赛事的官方赛制、赛场规则和赛事公告。
4. 为执行上述规则而作出的软件协议约束。

这里不是说赛事约束低于玩法，二者处理不同领域；发生实际冲突时须核对
适用范围，不使用一条未经审查的全局优先级猜测答案。

Academy 行为、52Poké 字段、国际版裁定、已有测试，都不能覆盖简中官方条款。
无依据的边缘交互应报“不支持／需要裁定”，不能随机选择一个结果。

每条可执行通用规则有稳定 `ruleId` 和 `sourceOfTruth[]`。每个卡牌效果也有
独立的卡牌来源证据。执行 trace 应同时记录两者：**依据哪条通则，
以及哪张卡的哪段说明改变了它。**

## 3. 内核分层

```text
原始 Wiki/其他 metadata（只读、仅资料来源）
  → 显式映射和来源核对
  → CardDefinition + CardPrinting
  → schema 结构检查
  → 地区版本、独立审批、handler、参数和赛制合法性检查
  → 对战状态机
       ├─ 有序效果解释器／已审核 handler
       ├─ 选择和费用
       ├─ 纯伤害结算
       ├─ 连续效果和触发队列
       └─ 昏厥、胜负和宝可梦检查
  → 各玩家可见状态投影／UI／AI
```

内核不得依赖 DOM、翻译字符串、全局 `liveGame`、系统当前日期或在线模型。
AI 和 UI 都只能提交同一种经过验证的命令。伤害预估不是实际结算；
预估不能消耗随机数、改变卡牌位置、选择结果或已使用标记。

### 3.1 状态与命令（基础主流程已实现，复杂交互仍在开发）

当前入口为 `public/rules/engine.js`。`OfficialGame` 接收独立审批后的 catalog、
显式 ruleset、两副卡组和随机种子；通过 `view(player)` 输出玩家投影，
`dispatch({player, expectedRevision, action})` 提交命令。
`snapshot()` 是可信宿主的私有存档接口，不是可发给玩家的网络消息；
`OfficialGame.restore(snapshot, {catalog})` 校验版本、catalog、结构和卡牌守恒。

私有协议当前为 `CN-game-dev-20`，不静默加载早期开发版存档。
`schemas/game-state.schema.json`、`schemas/game-command.schema.json`
配合运行时不变量检查约束此协议。内部 continuation payload 的更细 schema
仍须随完整效果解释器补齐，不能把私有存档校验等同于防篡改签名。

- 状态拥有明确的 `ruleset`、版本化 `format`、独立 `matchMode`、`revision`、`phase`、当前玩家、
  下一回合玩家、每位玩家的回合计数和起始奖赏配置。
- 分开保存牌库、手牌、奖赏、弃牌区、放逐区、场地、进化叠放、
  能量和道具。每张卡只能存在于一个位置。
- 保存伤害指示物个数，动态 HP 来自有效属性；HP 降低后也需要触发昏厥检查。
- 特殊状态、受到的招式效果、持续特性／道具影响、回合事实分别建模；
  不能用一个 `effects = {}` 同时清除所有类别。
- 所有外部命令须带预期 revision 和玩家身份；先验证合法性，再执行。
  拒绝命令不得消耗随机数或部分支付费用。
- 选择请求可序列化，带请求身份、可见目标、数量语义和来源。
  没有有效回答时不自动替玩家作出有规则意义的选择。
- 随机数来源可注入、可重放；随机源状态随存档保存。没有“抛到 20 次
  自动停止”等改写规则结果的隐性上限。
- 对手手牌、牌库顺序、反面奖赏及内部审批证据不经普通玩家投影泄露。

### 3.2 效果执行（顺序／保护／时限及基础触发已实现，复杂交互待完成）

`public/rules/handlers.js` 登记基础效果及其参数 schema 引用；
参数定义在 `schemas/handler-parameters.schema.json`。当前支持抽牌、
弃手、回复、放置／转放指示物、特殊状态、简单连续修正、首回合招式许可、
手牌／弃牌区基本能量的“最多”选择与逐张分配、伤害／效果保护、
有效弱点／抗性与明确的伤害忽略选项；另有指定区域选牌、展示、回收、
效果放于备战区、反面洗牌以及抽牌／奖赏的加入手牌前窗口。

`schemas/effect-program.schema.json` 定义递归的 `sequence`／`then`／`optional`
和具体动作；`public/rules/effects.js` 保存和推进显式执行帧。
后续依赖实际执行结果，不依赖“曾经发出选择请求”或“前文全部完成”。
卡牌专属 handler 仍须提供正确的使出／发动前置条件，
通用顺序解释器不从自由文本猜测它们。

`public/rules/ongoing.js` 以玩家回合计数和 `turn-end`／`checkup-end`
两种边界管理持续效果。目标身份与效果来源分开，不会把原本施加给
一只宝可梦的效果变成随来源移动的全场光环。玩家视图包含公开的有效
属性、持续效果及其规则 trace，不包含解释器内部帧。
宝可梦账本支持数值修正、弱点／抗性、保护、招式／撤退封锁和延后反应。
玩家训练家卡封锁另存于 `playerOngoing`，不是附加给战斗宝可梦的效果；
不因那只宝可梦免疫招式效果、回到备战区、进化或离场而自动取消。
连续来源的封锁与已经施加的有时限封锁仍分别处理。

`schemas/trigger.schema.json` 定义触发描述、事件事实、待处理来源、
持有者排序和检查前后安排。`public/rules/triggers.js` 处理精确匹配与
局部作用域验证，状态机在对应边界创建可恢复的窗口。
触发时保留原攻击者和致因，不把后来的战斗宝可梦或其他指示物效果
误认为原招式伤害；昏厥批次先完成全部反应再弃置并处理连锁。
局部触发不读取整张棋盘、不写入其他目标；跨持有者的全局依赖目前
需要进一步取得简中排序依据，仍是未完成项，不暗中套用国际版优先级。

效果选择和后续工作保存在状态中，不能在闭包或未序列化的回调里丢失。
延后反应保存原来源、固定受影响主体、将来窗口、时限和已审核的指令，
执行时保留造成事件的原攻击者；新施加的反应不追溯响应此前已发生的伤害。
其内部指令与原 handler 的权限分开验证，即使某分支不会执行也须检查。
当前支持的延后指令不能嵌套安装新的延后反应，也不能冒充新的招式伤害；
这不等于已经支持所有卡牌的最后已知信息和延后昏厥等机制。

尚未实现的 timing、特殊部署和操作必须被编译／执行门禁拒绝，
不能因为有 handler ID 就把卡牌宣称为可玩。临时门禁不是最终范围缩减，
仍须按后面的验收清单实现所有目标机制。

将宣告、合法性、费用、招式前效果、伤害、其余招式效果、
受到伤害的触发、昏厥、回合结束与检查区分为显式阶段。

- 效果顺序来自卡牌说明和 handler，不按 JSON 属性遍历顺序决定。
- “然后”依赖前文至少部分执行；“若希望”可跳过对应整体，
  不能据此随意减少一个明确指定的数量。
- 宣告费用和效果中的弃牌分开，特别是复制招式不能把说明文误当成先验费用。
- 原宣告招式身份与被复制的招式内容分开。
- 目标为战斗宝可梦、备战宝可梦或玩家时，保护效果的检查对象不同。
  “选择该目标”与“效果最终能影响该目标”也不等同。
- 同时触发的排序按简中对应章节规定的持有者决定；不得借用国际版
  2026 年“当前玩家统一排序”的裁定。
- 持续效果重新计算，非叠加组、状态替换、基础能量卡与能量个数分开处理。
- 离场、回备战、进化、退化、继承交换的清除和继承策略分别由条款控制。
- 持续到“下一个回合”的效果与持续到“下一个回合结束前”的效果，
  是否覆盖宝可梦检查不同，必须用事件边界而非单一数字期限表达。

### 3.3 效果来源的可用性与消除

`suppression.js` 独立推导哪些特性仍存在、哪些附着道具效果仍生效。
卡面定义、物理附着、已经建立的持续效果以及当前有效文本是不同概念：
消除一个特性不修改定义、不清空其次数，也不撤销此前已执行的后续效果；
消除道具效果不丢弃道具、不释放附着位置。

连续消除独立于普通数值修正先处理。来源节点按单个特性、附着道具、
竞技场、内建规则和已建立的时限效果区分，目标具有固定身份及明确的
持有方、位置、进化阶段、属性、规则框、标签和例外身份。
例外通过经审核的 `exceptAbilityIds`／`exceptToolNameKeys` 映射，
不能靠 UI 翻译或卡面名字子串猜测。所有真实特性，包括持续特性，
必须放在 `mechanics.abilities`；`mechanics.effects` 仅用于非特性的内建规则。
内建规则来源类别为 `rule`，不因消除特性而被一并抹去。

消除来源本身可能被别的来源消除，不能在一个遍历中按 JSON 先后来决定。
当前以已确定的依赖逐步求值。求值停滞时，剩下的来源必然含有互相依赖的环，
先按卡面文字：卡住的来源分成互不相连的部分，逐一枚举每部分的取值，
只有一种自洽（每个来源无效，当且仅当有生效的来源消除它）时按它结算，
记 `effects.remove-content`，这不是临时规则。每部分最多枚举 12 个来源
（`MAX_ENUMERATED_SOURCES`，2^12 种取值），更大的部分不枚举，直接按临时规则。
文字不允许任何自洽结果或允许多种时，简中没有裁定，在官方裁定之前按
**临时规则（待官方裁定）** `effects.remove-content-loop` 处理：取该部分最前面的环
（环外再没有未定来源指向它，即停滞部分最前面的强连通分量），环中每个来源
都被环里的效果消除，即全部无效，再继续逐步求值环外依赖它们的部分。
这些来源的 `removedBy` 列出它们还在等待的消除，记该规则编号和 `provisional: true`。
规则条目在 `public/rules/zh-CN/V20261019.js`，带 `provisional: true` 和指向
STATUS.md §6 的 `record`；`createRuleset` 校验标记与「临时规则（待官方裁定）」前缀。
它不是官方规则，也不擅用国际版时间戳规则。独立穷举 oracle 验证三节点全部 512 种
依赖图及三种输入顺序：196 图只有唯一自洽结果，求值结果都与之相同（其中 105 图
要枚举停滞的环）；其余 316 图与临时规则的独立模型一致。

有效来源接通主动特性宣告、连续 HP／弱抗／伤害／封锁、原生触发和
道具赋予的招式；已宣告特性的多个效果仍按说明文完成，不逐段重新宣告。
待宣告的后续原生触发会再次确认来源是否仍存在。
handler 的只读上下文提供 `effectivePokemon`，局部触发只获得
`subject.effective`，伤害公式可以据此计算实际“拥有特性”的宝可梦数量，
不能直接数不可变卡面特性数组。

消除来源的条件阶段只读取原始只读场面，不递归读取其自身的派生结果；
依赖派生来源的更复杂条件必须单独实现和审核。准备阶段也不执行隐藏
对手的连续效果，防止通过自己的有效 HP 泄露反面宝可梦信息。
官方的循环裁定（届时替换临时规则）、复杂特性／道具免疫与全部条件依赖仍须继续核对。

### 3.4 伤害模块（已实现基础管线）

`public/rules/damage.js` 处理的是**已经确定招式自身伤害后的子管线**，
不是整场游戏，也不负责自行识别卡牌文字。效果解释器应先确定实际抛币、
数量、目标、有效弱点抗性以及适用于该目标的修正。

同阶段修正先合计，再检查零值。按阶段输出可审计 trace；忽略弱点抗性、
忽略防守方附加效果、防止伤害分别处理。备战目标的普通规则允许显式卡面特例。
指示物效果另走效果通道，不套用招式伤害加减乘算。

当前已有简单连续效果收集、固定与已审核的实际公式、多目标伤害选择恢复、
指示物保护、基础反击和昏厥边界。主伤害及同一伤害阶段的附加目标使用
放置指示物前的属性／修正／保护快照，不能让前一个目标新受到的伤害
改变同阶段后一个目标的计算。说明文阶段的伤害另按当时场面计算。
每个目标单独明确适用的增减伤来源、目标位置和忽略选项；
对手战斗宝可梦增伤不自动用于自身反伤，主伤害的忽略效果也不自动继承。
所有伤害与其余招式效果完成后，才进入受伤反应和昏厥窗口。

复杂循环消除／免疫关系、完整最后已知信息和超出 3.10 的复制交互仍待完成。
纯函数和基础完整对局测试通过不等于这些交互已经实现。

### 3.5 检索、展示、洗牌与加入手牌前

`card-selector.schema.json` 和 `card-selection.js` 定义场外卡牌的明确筛选：
卡牌种类、规范名称身份、进化阶段、卡面 HP 上限、属性、规则框、标签、
卡面招式／特性身份，以及允许的筛选并集。没有通过 UI 文字猜测效果。
`printedHpAtMost` 读取不可变卡面，不读取场上的当前 HP 或临时增 HP。
`kind: any` 与指定类别分开，不能因为这一副牌刚好只有宝可梦，就把
“选择宝可梦”的隐藏区域例外替换成“任意卡牌必须选满”的语义。
具名能量属性筛选当前仅对基本能量开放；不能用特殊能量附着后的提供单位，
推断它在手牌／弃牌区里的卡牌类别。特殊能量仍可按类别或明确名称身份筛选，
更复杂的条件必须单独审核实现。

`cards` 指令明确来源、去向、数量、是否展示、可查看的牌库上方范围及
后续是否重洗。当前接通自己的牌库／手牌／弃牌区，去向为手牌、
弃牌区、重洗的牌库或备战区；没有默认为牌库顶底排序或对手盲选。
来源和目标相同、未知筛选、缺失洗牌语义等数据被拒绝。
独立 `shuffle` 支持指定玩家的牌库、手牌、奖赏；空区域不算执行，
一张牌也可算重洗。不依赖洗牌结果恰巧是否改变顺序判断“然后”。

查看内容与选择资格只给有权查看的玩家。即使不存在合格卡牌，
仍有私人查看确认窗口；未找到目标不省略应执行的洗牌。
备战区已满时，在查看牌库前跳过部署；不能先获得牌库信息再声称无位可放。
选定卡牌先进入独立解析托管，逐张放置时记录真实来源并处理对应触发，
不让第一个入场效果的抽牌抽走后面已选定的卡。中途空位被其他效果占满时，
尚未放置的卡返还来源，不超出上限，也不丢失实例。

普通场上宝可梦事件与 `beforeHand` 卡牌事件是不同 schema。
后者使用卡牌身份、实际持有者、抽牌／奖赏来源、回合和抽牌原因，
不伪造一个尚未出场宝可梦的 HP、特殊状态或 `pokemonId`。
抽牌和奖赏取得均逐张处理；准备阶段抽牌不误触发这类效果，
检索入手也不冒充从牌库上方抽牌。
当前有入场、能量附着、普通效果及嵌套抽牌的可恢复执行，
整张卡处理完后才继续下一张。场外特性不因场上特性消除而被错误抹去。

待入手卡暂存于 `resolving`，尚未属于手牌。只有确实宣告执行的效果才按规定
展示来源；拒绝可选效果不向对手泄露所抽的卡。已经由效果放于场上或附着的卡
不会被最终入手步骤再次拉回手牌。`afterUse` 仅决定仍在该托管中的卡的去向；
奖赏专用物品使用完可弃置，不能因此获得从手牌随意使用的许可。
从奖赏附着不消费普通能量附着，也不触发“从手牌附着”的特性。

原始 `source.origin` 沿后续帧保留。只防止“从手牌使出”的训练家卡效果时，
不会错误拦截来自奖赏的使用。恢复时校验入手卡、持有者、致因、回合、
批准绑定和最终处理锚点；特性身份与内建效果身份使用不同命名空间。
奖赏卡效果引起的新昏厥及其奖赏在继续原流程前结算，但不在相关处理未完成时
提前判定胜负；回合开始的入手效果完成后也进入昏厥边界。

更复杂费用、牌库顶底排列、反面奖赏交换、对手隐面选牌、超出 3.9 的场上牌返还、
完整场外主动特性、超出 3.7 的特殊能量条件、复杂最后已知信息等仍须继续实现；
不能把本节已有的私有选择和入手窗口扩张成所有卡牌均已可用。

### 3.6 使用条件与实际付款

`activation-cost.schema.json` 与 `activation-cost.js` 定义目前已实现的
**固定张数手牌弃牌条件**。它与效果中的 `discardHand`／`cards` 分开：
数量不足时不能宣告，不适用隐藏手牌选择零张或执行最接近数量的例外。
一张双重能量仍是一张手牌，不会因为附着后提供两份能量而支付两张卡的费用。
来源卡本身不能既作为使出／附着的卡，又被重复拿来付费。
招式的 `cost` 数组则是所需附着能量，不会自动弃置或消耗这些能量；
说明文中的能量弃置仍须作为相应效果单独实现。

不可变定义中分别保存：

- 宝可梦特性的 `costs`：整项特性的条件，不逐段效果重复收取。
- 训练家卡的 `playCosts`：从手牌使出前的条件。
- 特殊能量的 `attachCosts`：从手牌附着的条件，不错误用于奖赏来源附着。
- 独立触发／竞技场发动绑定的 `activationCosts`：对应那次发动。

每个费用行有独立 `costId`、卡牌筛选、完整张数和具体卡牌证据。
通用规则说明费用如何处理，不能单靠它证明某张卡具体要弃哪种卡、几张。
付费记录、哪些实例被弃置、次数和已接受声明属于运行时，不修改卡面条件。

付款可包含多个重叠筛选组。可支付性使用匹配算法，不用贪心或枚举所有手牌
子集；另有保留某目标卡、要求某卡进入弃牌区的证明接口。
玩家明确分配各组的卡，同一实例不能在两个组重复花费。
独立递归 oracle 对 1,200 个小规模分配／保留／必选组合给出预期。

不能只检查“手上够付”，还要检查后续效果能够执行。费用绑定的每个 handler
需要版本化 `canUseWithCosts` 和普通可用性检查；缺少已审核的证明时拒绝接入，
不默认任意效果都理解弃牌后的手牌或弃牌区。证明必须同步返回 boolean。
`cn.drawUntil@1` 在执行时计算真实手牌数，宣告检查则考虑费用及使出的训练家卡，
避免把“弃一张能量后抽至六张”误判为已经六张所以无法使用。

选择提交后先在副本中检查完整付款及其后状态。无效数量、重复用卡、
错分组、错持有者或使后续无法执行的支付全部原子拒绝；
不扣牌、不消费次数、不改随机数。确认后才扣全部费用、写入付款收据，
登记支援者／普通附着／特性／VSTAR 等次数并执行说明文。
可选触发的拒绝不消费费用。已接受声明不会逐段重新收费。

收据有独立身份、实际付款玩家、原来源和按组分配的实例身份，
沿 `sequence`／`then`／`optional`、抽牌及入手前嵌套窗口传播。
恢复时检查原卡牌条件和已提交记录，不要求已付卡仍在弃牌区，
因为后续回收本来就可能把它移回手牌或附着。附着事件另外保留附着条件的收据，
不与它随后触发的另一项特性／能量效果自身的费用混为一笔。

实体卡的 `owner` 与效果的关系视角不是同一件事。
`source.cardOwner` 记录实体持有者，`source.owner` 解释该效果的 own／opponent；
共享竞技场发动时后者是实际使用玩家。选择者另由 trigger controller 表达，
`payment.player` 是实际发动并付款的玩家，不能因竞技场来自对手卡组就扣对手手牌。
同一竞技场发动的多段效果共享的次数只登记一次，冲突或未知限制在接入时拒绝。

本节不是全部费用机制完成声明：能量要求和已附着能量的处理见 3.7；
其他支付区域及复杂支付关系、费用相关的更多状态触发／最后已知信息
仍须继续按简中依据实现。
跨持有者的费用触发也不能绕过尚待确认的全局排序依据。

### 3.7 印刷能量要求、有效能量和物理卡牌

`energy-mechanics.schema.json`、`energy-mechanics.js` 和 `energy-selection.js`
明确区分三个不互相替代的量：

| 概念 | 基础定义或运行时位置 | 用途 |
| --- | --- | --- |
| 卡面要求 | 招式的 `cost`、宝可梦的 `retreatCost` | 不可变起点，不因某场对战写回 |
| 当前有效要求 | `effective.attackRequirements[].routes`、有效 `retreatCost` | 在当时场面判断招式可用性／撤退付款 |
| 附着卡及有效提供量 | 实例的 `energy[]` 与 `effective.energies[]` | 一张卡可能提供零个、一个或多个能量单位，每个单位可有多个属性 |

D-09—12 的同属性增减合计后才截为零，使用安全整数计算；
D-13 消除优先于普通增减。E-32 的条件满足时，由已审核 hook 返回字面替代要求，
不会再加上普通能量增减；不满足时返回 `null`。
卡牌专属条件读取只读场面，例如受伤或本回合从备战区移至战斗场，
不由 metadata 自由文本自动推断。有效要求为零也不会解除睡眠、动作封锁或次数限制。
使用招式不会自动消耗用于满足要求的附着能量。

提供量在来源消除之后推导，特性／道具来源失效时随之恢复基础提供量。
E-39 的“各视作两个基本草能量”等语义使用**替换**，不是按来源数量不断乘二。
相同单位／属性多重集的重复替换不叠加；互相冲突的替换明确报需要卡牌专属裁定，
不擅自取最大值或最后遍历到的值。提供量阶段不读取自身尚未形成的派生输出，
准备阶段也不让隐藏对手来源改变自己的要求／提供量。

附着能量指令分别声明：

- `measure: cards | units`：选择的是卡牌张数，还是提供的能量个数。
- `selector`：卡牌身份筛选；`providedTypes`：当前提供属性筛选，两者独立。
  所有属性的一个能量在多种匹配属性中只计一次，不能选择关闭火属性来逃避弃置。
- `quantity`：公开区域指定／最多／任意／全部语义，不能改成国际版通用零到 N。
- 来源宝可梦、来源方／持有方选择、目标条件、一个共同目标或逐张分配。
  能量只在其持有者的宝可梦间转附，不转交对手。

C-01／C-10 的双重涡轮能量例子支持为一个或两个能量选择同一整张卡；
移动／弃置后绝不留一半单位在原宝可梦身上。当前仍缺乏明确简中裁定的
“为指定个数选择多张含冗余的多单位卡”返回 `unresolved-energy-quantity`，
且不移动卡、不消费随机数；这不是宣布该选择已经被官方判定非法。
全为单单位卡的普通超额仍按指定数量拒绝。

转附先完成全部选牌和目标计划，再按同一移动前场面检查效果保护、整体应用变化，
不让第一张的中间状态改变同批第二张的判断。计划可序列化；
恢复验证原持有者、原宝可梦、数量、目标归属和分配游标。
受保护的起点／终点仍能被选择，保护阻止实际转附时不触发依赖成功的“然后”。

特殊能量的不可变 `handAttachTo` 与 `remainOn` 分别限定从手牌附着资格和保留条件，
不将它们变成对战中随意写入的状态。C-10 允许选择无法保留特殊能量的对象；
转附后按保留条件进入持有者弃牌区。进化、入手前附着、普通附着和规则边界
也检查相应保留条件。基本能量不接受这两个特殊能量字段。

转附创建独立的 `energyMoved`／`origin: field` 事实，不冒充从手牌附着。
触发绑定若明确需要包含转附，可审核为 `energyAttached + includeTransfers`；
是否包含必须按具体卡牌证据决定，不能自动从宽泛中文“附着”一词推断。
这套协议不是所有能量变换、冲突优先级、能量付款或卡牌都已实现的声明。

### 3.8 效果进化、逐层退化和明确继承的替换

`evolution.schema.json` 与 `evolution.js` 分开描述三种不同操作，
不把它们都当成“用一张新卡覆盖旧卡”：

| 操作 | 核心变化 | 保留和清除 |
| --- | --- | --- |
| `evolvePokemon` | 从自己的手牌／牌库／弃牌区，将符合审核进化关系的卡叠放在固定宝可梦身上 | 保留伤害与附着，清除特殊状态及应在进化时清除的效果；记录实际来源和进化前卡 |
| `devolvePokemon` | 从最上方依次移除指定层数的进化卡，放入持有者的手牌／弃牌区／重洗牌库 | 保留伤害和附着，清除特殊状态及该目标的全部附加效果；按 C-13 记录为刚上场，不能普通同回合再进化 |
| `inheritPokemon` | 仅按说明文明确继承，用手牌／弃牌区的卡替换最上层；旧顶层进入指定区域 | 保留同一 `pokemonId`、下方叠放、伤害、状态、附着、持续账本、历史与特性次数；不是出场或进化事件 |

C-12 的效果进化时机与普通进化不同。参数必须明确自己首回合、
本回合新出场和本回合已进化三个条件，不从 UI 文本或 `evolvedTurn`
一个值猜测整张卡。已审核的卡牌限制可明确允许／禁止；缺少同回合再次
效果进化依据时使用 `needsRuling`，提交相应目标会原子报
`unresolved-evolution-timing`。这不是宣称官方普遍禁止该操作。

进化关系有通常的直接名称关系、跳过一阶，以及经具体卡牌授权的
任意一阶例外。二阶定义须有独立 `basicAncestor.nameKey` 和卡牌证据，
不能通过“这副牌恰好放了哪张一阶卡”推断神奇糖果的基础对象。
目录中若包含对应一阶卡，会交叉核对祖先关系；不要求一阶卡必须在卡池或卡组中。
缺少具体例外的来源证据时，不能只把关系改为 `anyStage1` 就当作真实卡牌已获批准。

目标和卡牌的选择可恢复，先保留原宝可梦／最上层身份及私有查看窗口，
完整确认后才移动卡牌。指定种类的手牌／牌库选择可按相应条款选择零张；
公开弃牌区仍按指定数量处理。牌库未找到符合卡也有私人查看确认及洗牌，
不会因为后端知道找不到进化卡，就从公共操作／目标列表泄露这一信息。
完整牌库检索的玩家投影按身份排序，不把内部牌库顺序直接展示出来。

效果进化记录真实 `origin`：从牌库进化不会触发“从手牌进化”的特性；
从手牌经效果进化仍使用从手牌事件。明确继承的替换不伪装成进化，
也不会借更换实体卡清空同名特性的已使用记录；其他独立特性不受这个记录限制。

退化把目标数量与每个目标移除的层数分开。只移除顶部连续的进化卡，
不可跳过上层，也不可将仅一张、经效果直接放于场上的一阶／二阶卡退化成空气。
任意层数可选择零层，此时不清除状态、不重记出场或冒称已经退化。
多个目标先选完全部层数，再按同一处理前场面检查效果保护并应用变化；
第一只失去特性不会改变同批第二只原本的保护判定。
`deckShuffle` 明确表示该指令包含后续重洗，而不是隐含把卡放在牌库顶／底。

伤害指示物不随新卡 HP 重设。变形、退化或特殊能量保留条件变化后，
仍进入正常昏厥、反应、奖赏与补位流程；因退化降低 HP 而昏厥属于效果致因，
不能冒充招式伤害。奖赏使用真正昏厥时揭露的形态，而不是已移走的进化卡。

`facts.evolution` 保存回合、真实进化前／后实例、普通／效果方式及来源。
E-23 条件由实际事件判断，不因为印刷进化前名称碰巧相符就自动成立，
也不因回备战区而删除。继承保留历史记录不代表新卡真的又进化一次；
卡牌条件仍需核对记录中的实际实例身份。退化清除这项当前进化事实。

本节不是全部形态机制完成声明。其他非继承替换、特例重叠方式、
对手隐面区域的进化操作、退化后复杂次数边界、源离场的完整最后已知信息、
与复制招式的全部交互仍须继续逐卡／逐条核对，不能凭这些基础原语批量批准卡牌。

### 3.9 场上返回、重新出场与非昏厥补位

`field-return.schema.json`、`field-return.js` 和 `cn.fieldReturn@1`
描述目前接通的 `returnPokemon`。目标明确给出持有方、场上位置、
卡牌身份筛选、公开数量、选择者、返回手牌／重洗牌库，以及附着卡的去向：

- C-02 的进化前卡与最上层一起返回；不把下层卡误当作能量或道具弃置。
- `attachments: return` 明确把附着卡一起返回；
  `attachments: discard` 明确只把宝可梦叠放返回、附着卡进入持有者弃牌区。
  具体使用哪种必须由卡牌说明和独立审批证明，没有通用猜测默认值。
- 返回对手的卡仍进入其持有者的区域；可以明确由持有者选择目标。
- 全批目标先判断效果保护，再移动卡牌；第一个连续来源离场不改变同批
  后一个目标原本的保护判定。未真正移动不会解锁依赖成功的“然后”或凭空洗牌。

离场退休的是整个 `pokemonId`，不是修改不可变卡牌定义。
该身份的伤害、特殊状态、个人次数、事件事实及目标账本不写进手牌里的实体卡。
其他宝可梦身上已经建立的效果、玩家封锁和玩家共享次数不因来源卡返回而自动抹去。
同一实体卡再出场时由 `newMon` 分配新身份；E-12 的个人次数可重新使用，
E-14 的玩家共享限制仍保留。

未宣告的原生触发既检查物理卡来源，也检查原宝可梦身份。
同一张卡已重新出场，不会复活旧身份尚未宣告的窗口或消耗新身份的次数。
目标账本已经因离场清除的延后反应也不再宣告；
但已宣告的多段效果仍可完成后续抽牌等处理，不把“来源离场”
当作任意取消整段程序的理由。

`returnEnergy` 与 `discardEnergy`／`moveEnergy` 共享严格的能量选择协议，
但有独立返回区域。按单位选择也整张移动多单位卡；附着能量返回不是新附着，
不触发附着／转附窗口，不恢复普通每回合附着配额。
从对手返回时只修改其区域，放回牌库后只重洗该持有者的牌库。
移除增 HP 来源后的真实昏厥仍在相关处理边界检查。

非昏厥离场和昏厥是不同的补位原因。C-02 说明了返回和清除，
I.E 规定相关处理完成后才判胜负；**这些不能单独证明非昏厥补位的全部时机，
I.D.5 的“双方同时昏厥”顺序也不能直接用于“返回＋昏厥”。**
因此 `promotion` 必须保存明确时机及其独立来源：

- `afterAction`／`afterRelatedResolution` 是可审核的协议执行能力，
  不是引擎自行选取的简中默认规则。真实卡牌只有具备适用依据才可批准使用；
  当前测试中的这些安排属于合成规范夹具，不是某张官方卡已获认证。
- `needsRuling` 在确实需要选择补位时显式拒绝猜测。
  复杂双边返回或返回与昏厥混合、尚无简中排序依据时，同样明确报未支持。
- 私有 `vacancies` 保留非昏厥空位的原来源和审核策略；
  补位 continuation 严格检查持有者、原因、来源、空战斗场和备战区候选。
  成功补位后清空记录，并记录真实的从备战区移至战斗场事实。

使用者在主伤害后返回，不会把后面的“原招式使用者”替换成新的战斗宝可梦；
已造成的昏厥、奖赏及回合结束仍处理。最后一只返回也不在相关处理途中提前判负：
后续入手前出场可以保住局面，双方最后宝可梦分别返回／昏厥也仍按简中胜负表处理。

这不是完整最后已知信息或所有区域替换完成声明。伤害前宝可梦离场、
已锁定昏厥的去向替换、非昏厥补位的完整默认依据、回牌库顶底排序、
其他附着卡类别及复杂场外区域交换仍须继续实现和审查。
本轮对未实现的伤害前离场同时设置接入与运行时门禁，不能由嵌套原生反应绕过。

### 3.10 作为这个招式使用：身份、内容和可恢复的调用栈

`attack-copy.schema.json`、`attack-copy.js` 与 `cn.copyAttack@1`
实现 C-18 的复制内容语义，不将它替换成第二次 `attack` 命令。
四个身份不能混合：

| 身份 | 当前协议 | 作用 |
| --- | --- | --- |
| 实际使用者 | 原 `pokemonId`／`player` | 属性、能量、进化历史、自身效果、伤害修正、own／opponent 视角 |
| 原宣告招式 | 原 `attackId`／`sourceId` | 使用身份和招式名不改变；来源卡也可能是赋予招式的 Tool |
| 被选内容 | `contentSource: {instanceId, attackId}` | 提供伤害和说明文，不提供该宝可梦的 HP、属性、能量或控制权 |
| 一次内容调用 | `copyId`、`execution`、`copies` | 区分嵌套实例，保存调用者的效果帧、计算选项和阶段 |

C-18 的通常规则是不要求被选招式的能量；因此复制“弃掉火能量”的招式时，
实际使用者没有火能量可以跳过这部分而仍造成伤害。
原宣告招式的能量、混乱等检查只执行一次。被选内容不重新宣告、不重复检查混乱，
不额外结束回合；多目标、反应、昏厥和奖赏仍在同一次原攻击的相应边界处理。
额外要求能量的卡牌特例必须显式声明按印刷要求还是有效要求检查，
不能把原招式要求与选中内容要求无意叠加或自动弃置能量。

D-06 的“拥有”只收集相关卡面印刷招式。当前支持审核后的己方／对手／双方
场上、战斗场、备战区、弃牌区及进化下层来源；可按明确身份筛选并排除实际使用者。
重叠来源去重，不把 Tool、特性或旧形态使用许可带来的额外可用招式当作当前卡拥有。
这也不把“完美无缺／回忆胶囊”等直接授予可用招式混为复制：
直接使用的宣告身份、能量与 C-18 不同，对应路径见 3.11，不能用复制原语冒充。

已接通复制前的一次抛币门控。结果来自对局随机源，不能由客户端传入；
选择收据保存实际结果、候选、来源和原指令，恢复不会重新抛掷。
普通选择仍须从公开合格招式中选一项，没有目标时不编造伤害。
嵌套复制每次都有可恢复的玩家选择，不以固定深度截断规则，
也不在一次同步循环中无限自动选择。
强制循环的最终裁定仍需独立简中依据，当前可恢复调用栈不是该裁定已完成的声明。

选中内容依次运行其伤害前处理、伤害、额外伤害包及其余效果。
公式、自身回复、能量弃置和进化条件都读取实际使用者；
借用的宝可梦即使无法使用自己的招式，也不因此失去“拥有”该印刷内容。
父子调用的计算选项独立保存／恢复；跨层说明文的特殊作用域仍需逐卡审核。
复制巨石丁的具名“下回合无法使用终极重锤”不会把原宣告招式改名；
没有指定名称的“无法使用招式”仍可限制实际使用者。
不同印刷攻击身份也可能同名；具名限制的审核绑定须把官方规范名称映射到
相应攻击身份，不能把槽位 ID 不同当作名字必定不同，更不能从 UI 翻译字串猜测。
复制内容中实际完成的抛币与未成立的内层复制分别计入各自执行范围，
不把外层的部分执行和内层“未复制”混为一个布尔结果。

原来源保留物理宣告卡与实际玩家，复制文本另存 `contentSource`／`copyId`，
并与选中记录和独立审批定义中的印刷攻击绑定。
借用对手内容不会扣对手资源或给对手抽牌；借用内容的实体离场也不抹掉
已经选择的不可变说明文。持续／延后效果继续保留两层来源，
而不是因 actor 的定义没有那段印刷文本就误判为伪造。
伤害与效果 trace 记录原招式身份、内容来源、调用身份和具体卡牌证据。

复制 GX／VSTAR 的配额处理不从国际版推断。`special` 强制声明时机策略及来源，
`needsRuling` 会明确拒绝猜测；使用者配额或仅原宣告标记的模式是可审核的软件能力，
本轮合成测试不能证明它们适用于某张真实官方卡。
原宣告已经消费的同类资源与此前回合已用资源分开记录，不重复扣借用者或原持有者。

复制选择、调用栈、coin 收据、原宣告内容及后续阶段均有严格 schema／不变量检查。
没有原使用者、没有按审核时序补出的对手战斗宝可梦、未知内容引用或变造的调用者
不被静默替换成另一只宝可梦。完整最后已知战斗属性、隐面复制来源、
超出 3.11 的直接授予机制、跨层特例和特殊标记的真实卡牌依据仍是后续验收项。

### 3.11 直接授予可用招式与明确的宣告来源

`attack-grant.schema.json`、`attack-grant.js` 和 `cn.attackGrant@1`
描述 D-06／D-09／E-37 的额外可用招式。它是独立的权限推导阶段，
不是往 `CardDefinition.mechanics.attacks` 追加可变数据，也不是执行 `copyAttack`。
直接使用时宣告的就是被使用招式本身，正常检查有效能量、睡眠／麻痹、
首回合许可、具名限制以及玩家的 GX／VSTAR 等资源。

权限来源可为连续特性、Tool、竞技场、特殊能量或非特性的内建规则，
必须按真实卡面类别登记；不能把实际特性放进内建规则来绕过消除。
先计算来源可用性和能量提供量，再生成明确权限描述；
提供者只读取只读事实和已完成的来源／能量阶段，不递归读取自身授予结果。
准备阶段不执行隐藏权限来源。

描述分别限定提供者关系、接受者筛选、位置、提供者是否在战斗场，
以及印刷招式的公开来源。`origins.subject: user` 把进化下层选择限定到
实际接受者自身，不把回忆胶囊误做成借用其他宝可梦下方的卡。
共享提供者的 `scope` 相对提供者判断，但己方／对手招式来源区域
相对实际使用者判断；不能因为竞技场属于对手就从对手弃牌区借用自己的权限内容。

拥有、可用和已宣告是三种不同事实：

- 获得权限不意味着在 D-06／E-37 下拥有这些额外印刷招式。
  复制及“拥有某招式”统计继续只读相应卡面，不将权限推导结果当作卡面内容。
- 来源被消除、离场或内容移出资格区域时，未来的可用列表重新计算。
  已经合法宣告的处理保存当时的权限收据，不在每段效果中重新宣告；
  不能因中途权限消失就取消已接受的后续伤害或效果。
- 被使用内容仍只提供招式，实际属性、伤害修正、自身效果、能量和控制者
  都来自真实使用者；不把提供者或内容持有者当作实际使用者。

`grantId` 与 `copyId` 区分两类内容来源，二者不能同时装在同一来源对象上。
直接声明收据保存实际使用者、选中内容、提供者、审核绑定和当时权限描述。
未来持续／延后效果仍能核对已经离场的提供者及原印刷文本；
直接得到的招式若再执行 C-18，复制子范围保留原直接宣告身份，
并通过权限／复制记录链追溯原始授权，不冒充无来源的原生攻击。
来源链迭代验证，拒绝重复记录、缺失提供者或循环证明。

多个来源可能给出相同 `attackId`，但源卡、内容或许可不相同。
`referenceId` 是该可用项的明确引用，不改变招式名称或使用身份。
无歧义时仍可只给原 `attackId`，或显式携带其准确引用；
有歧义时必须从 `legalActions` 给出的引用中选择，不能按数组先后任取一个来源。
错误引用不会被自动忽略或退化成另一项合法攻击。
玩家投影提供每个可用项的内容／权限来源和有效要求，不公开内部收据与解释器帧。

当前实现对应普通公开来源的连续权限；限时／玩家级临时授予、隐面内容来源、
更复杂的依赖反馈及特殊规则仍需继续核对，不代表相关真实卡牌已自动获得批准。

### 3.12 招式失败：宣告检查与卡面自身条件

`attack-failure.schema.json` 和 `attack-failure.js` 区分两种语义：

- 宝可梦受到的 `attackCheck` 是持续账本里的条件检查，不是不能宣告招式的
  `restriction`。按 I.A-01 的 2-a 先检查，通过后才检查混乱。
  这里失败不消耗 GX／VSTAR、不记作使用过招式，但仍结束回合并进入检查。
- 印刷招式可有静态 `failureCheck`，其硬币条件及卡牌／勘误证据参加定义审批。
  通过前述检查之后，自身条件即使失败也算已经使用招式，消耗相应特殊额度；
  不执行招式伤害、附加伤害、回复、抽牌或其他正文。

固定次数检查必须抛完所写次数；直到反面没有人为二十次截止。
结果只能由内核 RNG 产生，不能从命令带入。每个当前／暂停的执行上下文保存
独立 `failureReceipt`；恢复验证其条件、次数、终止位置、计数和成功值，
不会重新抛已经完成的硬币。无自身条件时该字段必须为 `null`。
运行事实统一为 `facts.lastUsedAttack`，不再用“成功伤害”误称“使用过”。

普通、直接授予及纯 C-18 复制链都保留实际使用者／原宣告身份。
仅由复制构成的链中，被选内容自身失败会终止整次招式；
已有其他伤害／效果的复杂组合不做猜测性回滚，明确等待取消作用域依据。
多个外加检查只有**明确审查的同一非叠加组且条件相同**才合并；
重复实例 ID 或相同文字不构成分组依据，不同组的未决顺序仍拒绝。
非硬币失败（如 E-33 FAQ3）和自身失败结合伤害前效果仍未完成，
不把这套硬币协议等同于全部失败条件。

### 3.13 实际回合与战斗事实账本

`battle-history.schema.json`／`battle-history.js` 已接入私有状态的
`battleHistory`，替代原来缺少原因的玩家 `history` 宽对象。
保存完整的实际回合顺序，不用 `turn - 1` 推测上一对手回合；
表示法可容纳同一玩家连续回合，但额外回合效果本身尚未实现。
恢复核对全局回合、当前玩家、先攻者和双方真实回合次数。

账本记录实际发生的昏厥、从备战区移入战斗场、从手牌使出支援者、
实际回复的 HP。它不从现有弃牌、能量张数、已用额度标记或“曾要求回复”
推测行动。E-11 区分任意昏厥和招式伤害原因；检查中的 `during: null`
不算任何玩家的回合。多只昏厥仅让条件成立一次。
E-24／25／26 查询真实使用者，不读取被复制卡牌原持有者的状态。
新增条件招式集成测试实际执行“事实发生→条件公式→伤害管线”，
不把单独存在的查询函数当作接入证明。

昏厥批次在锁定时保存原因、时界、原卡和奖赏数，并形成独立日志收据。
历史事件在昏厥处理提交时写入；昏厥触发中的回复不能重写原锁定原因。
恢复同时检查待处理批次、触发窗口、历史记录与原收据，
不接受移到其他时界、替换来源／卡牌／奖赏数或将已昏厥身份重新用于场上。
离场后的物理卡与复制／授予来源继续按原目录及选择收据核对。
这仍是可信宿主的协议一致性校验，不是对私有存档签名或玩家身份认证。

### 3.14 灼伤数量变化的实战接线

`cn.burnCounters@1` 的严格参数为 `{effect: burnCountersDescriptor}`，
连续载荷与来源可用性、范围、属性、Active 限制走同一管线；
固定目标的持续账本也可承载它，不另造移动光环。
检查的灼伤步骤先过滤实际有效来源，再由 `checkup-effects.js` 聚合：
**有替换取最大值一次，只有没有替换才用默认两个**，不叠加，也不把默认值混入替换集合。

零或一个的明确替换保持其数值；它们不表示防止灼伤或恢复状态。
仍按实际数量放指示物、抛恢复硬币并在正确边界确认昏厥。
多个并列最大来源都留在 trace 中，不给某一来源虚构优先级。
特性／道具消除、来源离场，以及“回合内”与“直到回合结束前”的检查覆盖差异
由原有来源和时限系统决定。聚合说明 trace 不是第二次灼伤行动。

### 3.15 HP 与指示物的精确数值边界

卡面 HP、伤害指示物及其乘十转换都受本 JSON／JavaScript 协议的安全整数
表示范围约束；这是软件表示边界，不是声称官方卡面有这个人为 HP 上限。
有效最大 HP 用 BigInt 精确合计再核对表示范围，不因来源枚举顺序发生浮点舍入。
恢复也执行该检查，不延迟到视图才发现非法数值。
当前 HP 仍只派生，不增设第二个可修改的 HP 字段；
未来回合的回复、移入 Active 或招式使用事实会被拒绝。

### 3.16 招式手牌失败条件和私有牌库操作

E-33 FAQ3 的“弃指定张数，否则失败”不是 E-30 的宣告费用。
`attack.failureCheck.handPayment` 使用 `attack-commitments.schema.json`：
宣告时即使资源不足仍可使用招式；随后只能完整弃置指定张数或选择零张失败，
不能先弃一部分再失败。资源充足也可主动选择零张。该招式已使用，
配额和使用事实不撤销，但伤害及剩余正文均不执行。
每次宣告有独立 `attack.id`，执行帧区分 `failure-check`／`body`，
请求与成功付款收据绑定真实使用者、原手牌、原内容来源和当前宣告；
复制对手说明文也从实际使用者手牌付款，不消耗对手资源。
隐藏筛选条件的可支付性不改变对手看到的等待阶段。
这只补齐明确手牌弃置这一类，不自动放开所有失败条件／伤害前组合。

`deck-window.schema.json`、`deck-energy.schema.json` 分别描述：

- `inspectDeck`：只查看自己上方固定窗口，按明确选择条件加入手牌，
  余下窗口单独反面重洗后放到牌库底。未查看段的次序不变；
  不是重洗整个牌库，也不是保留余牌在顶端。
- `attachDeckEnergy`：从自己牌库全体或固定上方窗口选择物理能量卡，
  指定己方接收对象和单目标／逐卡分配，再重洗剩余整个牌库。
  不经过手牌，不消耗普通手牌附着次数，不触发“从手牌附着”的限定事件；
  多张附着按物理张数产生事件，实际保留仍受特殊能量的条件约束。

两个 production primitive handler 为 `cn.inspectDeck@1` 和
`cn.attachDeckEnergy@1`；“production primitive”不表示真实卡牌已获准入。
原牌库在所有选择完成前不变。私有 `deckChoice` 捕获原始牌库／窗口，
绑定当前回合、来源及独立选择／分配日志，恢复时重算窗口与选择边界；
原始牌库收据仅宿主可见，连操作者也不能从历史事件读取未查看的牌库顺序；
操作结束后也不解除该限制。完整答案合法后才一次提交移动。不能把被改过的计划自身当作原始证据，
也不能把已启动操作插入队列重放。牌库窗口只给实际玩家；
洗牌后的子序列、RNG 和私有回执不出现在任一玩家的公开投影中。

### 3.19 印刷伤害、数值表达式与伤害阶段事实

`printedDamage` 只记录卡面：空白仍为 `null`，固定／加／减／乘符号保持原样。
一个明确的 `resolve-attack-damage` 公式按经审核的说明文执行，
不再因为伤害栏空白或为固定数值就被忽略；没有公式的非固定伤害仍明确拒绝，
多个公式也不擅自取首项／末项。无需把实际结果或虚构的“0+”回写卡面。

`battle-value.schema.json`、`battle-predicate.schema.json` 定义有限、非脚本语言：
整数常量、加／减／乘、明确的宝可梦统计、奖赏查询和条件取值；
谓词包括整数比较、all／any／not及已知存在性。原生 `cn.damageValue@1`
桥接主伤害；`damage.amount` 可为已有数字或同一表达式，以支持按所选目标造成伤害。
这些不是自由文本解析器，不执行字符串代码，也不能签发卡牌审批。

宿主分别提供 `self`（真实使用者）、`ownActive`、`opponentActive`、`target`。
换位后使用者不被新战斗宝可梦替代，C18借用说明文也不借用对手的HP／能量。
统计区分指示物个数、当前有效最大／剩余HP、撤退所需能量、
物理能量卡张数与提供单位数，不作隐式单位换算。
未知字段／缺失事实不当零，明确 `null` 才表示对象不存在；
未决奖赏不能变成0。校验完整静态AST，再短路读取实际选中的运行时分支。
原型上的 getter 也不能补充缺失的 kind。

中间整数用 BigInt 保持精确，包括很大数相减后成为合法结果。
仅整个基础伤害表达式完成后将负数归零，再核对软件的安全整数和十点单位边界。
结果0仍遵循B-02／B-03：不被之后的伤害加成重新变成正数。
计算／检查条件本身不算执行了一个伤害效果，和“招式失败”也不是同义词。

I.A-01.4、B-08／B-09要求普通备战／自伤参与伤害阶段，不能当作普通后续效果。
`cn.recoilDamage@1` 因此与普通伤害一样使用步骤4，而非默认步骤5。
伤害模型连同数值事实在本阶段开始前锁定；主伤害先写入指示物后，
后续所选目标的计算仍读同一阶段原值。不同目标先完成全部计算再施加指示物。
只有具有独立卡文依据的特殊处理才可使用其他时序，测试用特殊handler不等于真实卡认可。

私有 `stage-snapshot` 回执绑定宣告 frame／复制 scope 和完整冻结模型。
恢复不能独自更改或删除模型、数值事实、阶段后续任务及回执，
也不在恢复选择时重新计算主伤害。回执在结束后仍仅宿主可见，
双方投影即使收到误标可见性的原始对象也排除它。
这是内部一致性检查，不是网络存档的密码学认证。
数值快照是“计算当时”的事实，不是卡面属性，也不成为宝可梦当前HP的第二个权威值。
私有协议升级为 `CN-game-dev-17`。

伤害硬币统计由下一节接通；任意对象分配、数值驱动的全部持续载荷及其他复杂条件仍需继续。
本节不能替代相应条款、真实卡牌回归、印刷和生产发布审批。

### 3.20 伤害计算中的硬币、命名统计与可恢复性

B-01／B-02的掷币是基础伤害计算，不是D-01的招式失败检查，也不是任意后续效果。
`damage-coins.schema.json` 描述固定次数和直到首次反面两种规范：
固定0次不消耗RNG，直到反面不得有任意20次上限；收据记录真实结果与正／反／总次数，
不借用失败收据的 `passed`。`coin` 数值叶节点只读取当前内容执行的已记录计数。

`cn.damageValue@1`、`cn.damage@1`、`cn.recoilDamage@1` 接受可选
`rolls: [{key, spec, condition?}]`。固定次数可为明确整数或当前数值表达式，
可按已经完成的先前硬币统计决定后续计划。条件不成立留下显式跳过记录，
不产生一个“正面0”的假收据；若实际公式读取这个不存在的结果则明确拒绝。
同次内容执行中，key跨binding唯一并共享，因此主伤害与备战包可复用同一次掷币；
不重复掷币来凑第二个伤害值。

第一版计划协议要求回调输出与经审核的binding参数计划完全一致，
不能在执行器中塞入未声明的rolls而被忽略。声明版本、capability及回调代码都进入目录／发布指纹。
阶段4先按binding／计划顺序执行，再计算伤害并锁定数值事实。
主公式有已知对方战斗目标；额外包的目标尚未选择时必须为未绑定，
不可偷偷当作对方战斗宝可梦。需要先选目标再掷币的完整计划仍须继续实现。

每个execution保存独立 `damageCoins`，并以frame／copy／回合／来源绑定
私有prepared回执及RNG起终点。复制内容创建自己的命名空间；
返回调用者恢复其计数，但不回退已经推进的全局随机流。
公开记录只有实际可观察结果和计数，没有RNG状态或宿主准备数据。
空计划仍保存已完成准备的边界；`null`专指尚未进入准备，不能混作零次。

恢复先检查原始计划、条件、动态次数、停止点、来源、计数和回执，
并以RNG起点的克隆重放作一致性审计，不消费真实RNG、不发布新掷币。
阶段4冻结的硬币计数必须与执行收据相同；后续选择和JSON恢复不会再掷。
私有回执即使在结束后也不能改为玩家可见；这仍不是网络存档的密码学认证。
实际翻币属于已执行的内容，不能因伤害为0就假定之前什么也没做；
复制失败的复杂取消仍受既有门禁约束，不擅自回滚已经发生的前文。

私有协议为 `CN-game-dev-18`。非伤害效果中的通用掷币、目标先选的多阶段计划、
硬币结果驱动的所有动作数量及其他未完成机制仍不因本节自动获支持。

### 3.21 私有奖赏交换与整手牌洗底

依据C-20 p41、E-34 p73、E-35 p73—74，`exchangePrizes` 专门表达
查看自己的全部反面奖赏、依明确的印刷属性选择一张、与正在结算的道具／支援者本身交换，
最后将整个剩余／换入奖赏池反面重洗。它不是昏厥后“拿取一张奖赏”的通用别名，
不会改变奖赏张数或伪造获得奖赏的历史。选择不限条件时必须选一张；

已结束的历史记录也不能重新标成公开或泄入玩家投影。
事件种类有严格且互斥的payload schema，不能把私有记录改名为finished后直接公开。
公开finished带本次请求id，并核对唯一原请求、实际结果和卡面指定的展示权限；

普通非交换训练家的待选目标和抽牌continuation同样必须保留其唯一finalizer，

通过加入手牌前窗口使用的来源绑定实际 `entry-finish`，遵守同一不重复归位原则。
保存中的选择、窗口、来源、持有者、回合、finalizer及私有事件相互核验，

### 3.22 全部／同时回复与实际回复结果

C-06 p29中的“全部回复”指移除全部伤害指示物，不是回复一次印刷HP，
也不创建可修改的currentHP或以当前最大HP限制移除量。旧 `cn.heal@1`
仍保留固定数值单目标协议；新增严格的 `healPokemon`／`cn.healPokemon@1`：

```js
{
  op: 'healPokemon', side: 'own', target: 'any',
  selector: { kind: 'pokemon', stages: ['stage1', 'stage2'] },
  selection: { kind: 'all' }, amount: 'all',
  discardHealedEnergy: true
}
```

`amount`也可为明确的正十点倍数，最多移除已有指示物；目标、数量、筛选和后续策略
均显式，不接受预先提供的healedIds、保护掩码或运行时HP属性。
筛选中的名称、阶段、HP仍是印刷定义，类型使用实际有效类型；
进化宝可梦不能通过叠层厚度、进化时点或“不是基础”猜测。

单体回复训练家／特性不能指定健康对象制造使用资格；多体范围可以包含健康对象，
但主动所选集合至少有一只有伤。独立can-use只看能否实际选择有伤对象，
不要求这些对象附有能量，也不因效果保护而禁止选择。
攻击中没有可回复对象时，该叶不执行，不取消其打印伤害或剩余内容。

纯模块 `healing.js` 规划每只主体的before／after／removedCounters，
以及仅包含实际移除至少一个指示物者的 `healed` 集合。
宿主先收齐本批全部选择、冻结所有回复保护判断，再整体改变指示物；
仅正回复量写本回合事实及heal历史，不给健康／受保护对象记假回复。
牌面、最大HP修正、附着卡及其他特殊状态不因回复本身而被改写。

E-19 FAQ3 p63的 `discardHealedEnergy` 是明确的关联后段，不是假装已实现通用结果变量AST。
它只处理本次实际回复集合，不能再次扫描所有进化宝可梦，不能借 `healedTurn`
混入先前回复者。完成全部回复及连续保留条件后，重新检查这段的当前保护与实际附着，
统一确定全部可弃物理能量卡再移动；多单位能量仍只移一张，不误弃道具或进化层。
原生合约同时声明 `healPokemon` 和 `discardEnergy`；即使某分支不会执行，
也不能漏声明后者后再通过关联开关弃能。

公开的待选窗口保存当前主体ID、顶层实体卡和指示物数量，并绑定来源、
回合及唯一requested收据；恢复重算候选和数量，不把旧窗口当当前状态。
started选择不能复制成排队工作，local主体通道不能冒用全局批次。
完整回复／关联弃能本身不要求新的玩家选择，作为一次原子叶处理；
后续保存不重回复、不重扣次数、不重复弃卡或借复制父帧结果。
能量保留与HP改变可能导致的昏厥留在相关效果完成后的既有边界核对。

声明回复指令的 handler（含嵌入程序）使用独立 `programId` 和私有
`effects.execution` 日志。`scheduled` 固定实际定义绑定、来源、回合、
事件、进入手牌前上下文及费用收据，`opened` 固定完整静态程序，
`advance` 逐步记录控制节点展开、接受可选效果和叶执行结果。
恢复时从原程序重放，要求当前 `action`／`frames` 完全一致；同一调用在
队列、当前选择、抽牌 completion 和复制招式父 continuation 之间只能保有一个活动引用。
原生回复程序还必须等于不可变定义参数，不能通过同时修改待选 action 与请求历史
升级回复量、添加弃能或嫁接第二次效果。完成的调用不能重新启用，
未执行的调用也不能靠删除待办工作悄悄丢失。所有执行日志对双方玩家均不可见。
来源身份也必须能由卡种和批准绑定独立支持：物品／支援者不是场上效果来源，
非手牌来源必须对应其原有的加入手牌前触发。即使同时改写所有执行及选择日志，
也不能把手牌使出的物品改称场上来源，以绕过只保护手牌训练家效果的载荷。

该日志是承载 II.A p19、E-19 p62—63 顺序语义的软件协议，不是官方另行规定的
签名格式，也不是任意可编辑全量宿主存档的密码学认证。自定义受审 handler
的输出仍以可信宿主记录为边界，不从 JSON 自带声明签发代码或卡牌审批。

第二十二轮验收的私有协议为 `CN-game-dev-20`。这不自动实现任意伤害指示物分配、所有条件／结果集
传播、源离场全LKI、特殊胜负时序或真实奥利瓦／芽米等卡牌的全部印刷审批。

### 3.23 固定总数的指示物分配（限定子集）

第二十三轮私有协议升级为 `CN-game-dev-21`，新增独立的固定非负总数指令
`distributeCounters` 和 `allocateCounters` 数值回答命令。
公开窗口保存顶层卡与原始指示物；答案按宝可梦ID提交正数份额，不用重复字符串模拟个数。
候选非空且总数大于零时须足额分配，不能少放；零／无对象不强迫不存在的分配，
唯一对象可自动承受全部数量。总数不代表每只数量，也不受剩余HP限制。
验证完整答案后，宿主先冻结全部所选对象的效果保护，再计算并一次提交所有计数；
受保护份额损失而不重分配，指示物不会产生招式伤害或回复事实。
数值请求与原窗口共用唯一nonce，完整程序另有独立调用身份；
不能借旧请求或修改pending.id授权另一次分配。主动原生物品／支援者／特性
还须判断完整使用资格，不能只因有候选便宣告；第二十四轮另补E29专门许可，
这与获准效果仍可选择受保护对象分开，不是所有旧handler的通用可执行性证明。
第二十三轮整体验收见 `IMPLEMENTATION.md`，不提前开放任意数量、多来源转放、
动态总量或复杂付款后依赖，也不代表全目标完成。

### 3.24 使用资格与保护的使用规则

第二十四轮私有协议为 `CN-game-dev-22`。`canUse`／`canUseWithCosts` 的局部候选判断
不是“存在对象就一定可使用”；宿主对已审原生回复、指示物和互换叶另外核对实际
受影响主体、保护来源及完整使用资格，不把规则推广成任意卡文解释器。
费用导致的手牌／弃牌区变化、正常使出的结算区预留、使用事实及能量保留，
在脱离真实状态的投影中落实后才判定；投影不提交卡牌、次数、队列或随机数。
存在一份完整可用付款即可证明可宣告，实际选择仍须单独核验。
首个matching失败不能代替全部搜索，软件证明预算耗尽也不能伪称官方禁止。

保护说明新增必填 `useRule`：

- `ordinary`：获审的一般保护，没有声明E29使用许可；不因可选对象存在而自动放行。
- `CN.E29`：按固定进阶p68—69审查的手牌物品／支援者保护许可；
  严格要求effects通道、trainer类别、hand来源和明确的item／supporter类别。
  卡牌可使用，但被防止部分仍未执行，不能据“可使用”解锁then。

该字段是不可变效果定义的规则分类，不是基础HP、当前HP或运行时的“已获授权”位。
第三方原文、来源筛选或卡名不能自动决定分类，旧内容审批不能覆盖改变后的分类；
原始52Poké资料仍保留不变，未审映射拒绝进入正式目录。
为避免未锚定账本授予许可，拒绝timed／ongoing的CN.E29载荷；
第二十六轮新增独立Stadium卡主体，仍禁止把竞技场卡自身当Pokemon self主体。
竞技场作为宝可梦盾的来源也可支持，不混同这两种受影响主体。
未审的一般／E29重叠仍报未决，不能任意挑优先级；已有另一个确定可用部分则不被其阻塞。
自定义handler的额外条件不会因继承原生标签而被覆盖，原生代码识别不是对恶意宿主的认证。
其他激活、触发与费用语义仍逐项审查，不能用此限定子集宣称全体CardDefinition已经合规。

### 3.25 原始程序与暂停控制面的恢复完整性

当前私有协议为 `CN-game-dev-25`。所有排队效果调用都必须有唯一programId，
而非仅回复／分配指令；私有scheduled／opened／advance重放当前动作与完整控制帧，
不能把一个调用分裂、丢掉或从已完成历史重新启用。
静态原生输出还须与不可变参数及原始source重新生成的程序一致。
drawUntil等上下文输出不从当前局面假造原始输入；独立打印上界与原私有日志分别约束，
不把同一份可编辑JSON变成对任意宿主的认证。

每次真实玩家暂停均封存私有 `selection.request`。
收据复用原typed pending并记录queue／attack、serial／revision、时钟及空位，
在drain及revision完成后生成，避免记录尚会变化的中间队列；
不递归包含自身events或复制全部玩家资料。
恢复时完整比较请求和暂停控制面，未知ID、重复／缺失收据、替换原选择或嫁接未来工作均拒绝。
玩家视图屏蔽整个命名空间及可识别的请求／控制面结构，不因改日志标签授予隐面信息。
这仍不是对任意重新编码或任意恶意应用宿主的密码学防护。

纯复制链被借用招式的自身失败中断时，按已审纯复制范围将每个原copy叶完成为false，
再清除攻击栈；不允许把程序活引用遗留到下回合。抽牌预算及转放中间量另作静态边界核对。
离线schema的const比较采用严格JSON结构等价，不以JS对象constructor区分同值记录，
也不调用getter／valueOf等钩子；固定奖赏来源const不因此放宽。

### 3.26 场地卡主体与弃牌去向

`discardStadium`针对当前实际物理场地卡，使用打印Trainer选择器及相对使用者的
own／opponent／either范围；不把它建模为拥有HP、属性或指示物的Pokémon。
`stadiumProtection`是当前场地自己提供的self／effects连续效果，不能挂在其他卡、
后来进入同槽位的场地或可编辑的持续账本。普通／E29使用门槛与实际是否执行仍分开；
正常使出异名场地的替换是I.B-04规则，不是会被Item／Supporter盾阻止的效果。
原场地离场后重算HP、能量保留及新的致死事实，沿用正常昏厥边界。

不可变根字段`CardDefinition.prismStar.sourceOfTruth`明确分类棱镜之星，
并要求同名一张、基础规则框宝可梦／特殊能量等相应约束与逐卡证据。
所有原本进入弃牌区的路径统一查询`discardDestination`：这张物理卡改进原持有者
放逐区，不连带放逐普通附着卡、不取消昏厥奖赏，也不因单纯使用在场特性而移走。
费用仍须足额，替代后的实际移动可计入普通then；后文查询弃牌区不能找到已放逐卡。
不从◇、翻译名、52Poké或运行时标记推断身份；带标记／不带标记的不同卡名不合并。
不提供通用lost回收或任意去向覆盖；竞争替代与特殊“实际进入弃牌”触发另行审查。
来源及明文／通则推导的区分见`FIELD-CARD-SCOPE.md`，不批准真实整卡。

### 3.27 现场选择拥有的招式并禁用

`disableOwnedAttack`先选择对手当前战斗宝可梦最上层卡面的一项招式，再建立
`ownedAttackRestriction`账本。候选是打印成员关系，不是legalActions；
不按能量、已用GX／VSTAR、旧锁、道具／特性授予或下层进化卡筛选。
非空候选严格选一，包括仅一项也有完整暂停；零候选不附锁，其他内容仍照常执行。
效果保护阻止附锁但不改变候选，防伤害保护不是防效果，performed独立控制then。

首批动作固定为招式resolve正文、对手Active、nextOpponentTurn与回备战／进退化清除，
不是可任意传attackIds或修改卡面的编辑器。专用ongoing载荷不能由continuous、
lasting、反应或客户端自行签发；它必须关联原打印窗口、程序／位置、原暂停、
实际回答、应用／完成与清除收据。清除另须指向原`battleHistory`实际事实，
并在原选择的historyIndex之后；相邻通用日志本身不是转场或到期证明。
进／退化及完成回合的专用事实只在本机制真实清锁时记录，备战／KO沿用原实际事实，
离场须原Pokémon身份已不在场。期限和原目标固定，不随施招者离场而失效。
继承替换按D19保留附加效果，通过实际from→to链保留原参考，不伪装进化清锁。

匹配保留实际直接使用路线：grant的执行者instanceId不等于内容来源；
相同获审definitionId＋attackId可以表达相同打印语义，不凭跨卡ID碰撞误锁。
C18复制内容不替代外层宣告身份。不同定义直接提供的同名招式若真正可宣告，
固定原文仍缺匹配依据；视图明确列`unresolvedActions`，显式宣告报未决，
其他确定合法路线仍可用。不能把未决静默当作禁用／许可，也不整体禁止额外招式。
详见`OWNED-ATTACK-LOCK-SCOPE.md`；原私有收据不是恶意宿主的密码学认证，
也不是伽勒尔堵拦熊或其他真实整卡已获审。

## 4. 卡牌 schema

### CardDefinition

规范：`schemas/card-definition.schema.json`，JSON Schema 2020-12。

- 不含图片、卡组张数和对战实例状态。
- 可选根`prismStar`是获审的静态特别规则，不是运行时区域或可编辑去向。
- `name` 是该规则版本下的卡牌名称，`nameKey` 是经核对的同名规则身份，
  不是从英文名称或翻译结果临时生成。
- `kind` 区分宝可梦／训练家／能量，并约束各自的 `mechanics`。
- 明确保存进化来源、属性、弱点运算和数值、抗性数值、撤退费用、
  招式、能力数组、规则框、奖赏数量及规则标签，不猜默认卡面数值。
- 二阶宝可梦的 `basicAncestor` 保存经核对的基础名称身份和独立来源，
  它是规则定义，不是对战中实际从哪张卡进化的历史。
- `printedDamage` 把固定／加／减／乘的印刷语义与效果实现分开；
  没有伤害数字用 `null`，不能把效果型招式当作零伤害普通攻击。
- 能量的 `baseUnits` 是能量个数，每个 unit 可以有多个同时有效的属性；
  支付费用时每个 unit 只能支付一次。能量卡本身仍只有一个实例身份。
- `effectId` 标识单个效果；`handlerId` 选择受信任代码登记的实现，
  不是可从数据加载的任意脚本路径。每个 handler 必须具有严格参数
  schema、适用规则版本、所实现的规则 ID、卡牌证据和测试。
- 基础 schema 不把所有 handler 参数压成一个宽松通用对象就算完成。
  执行门禁必须调用对应 handler 的严格参数验证。
- `implementation.status` 为数据状态声明，不是审批凭证。进入执行还需要
  独立、内容绑定的审批目录。改过 HP 或效果后旧审批必须失效。
- 定义／印刷进入规范摘要前须为严格有限、无环、own-data JSON，
  optional `undefined`、getter、隐藏字段等不能被摘要忽略而留在执行对象中。
  普通／null-prototype JSON记录可同值，不把JS原型当作卡牌身份。

### 基础属性、运行时状态和派生属性

三者不能合并成一份会被对局直接修改的卡牌 JSON：

| 层 | 位置 | 例子 | 写入方式 |
| --- | --- | --- | --- |
| 卡面基础属性 | `CardDefinition.mechanics` | `hp`、卡面属性、弱点／抗性、撤退费用、招式和特性 | 审批后只读；对局不修改 |
| 运行时事实 | `GameState` 中的卡牌实例、场上宝可梦及账本 | `counters`、特殊状态、附着卡、次数、伤害致因、定时封锁 | 规则引擎通过受验证的命令修改 |
| 当前有效属性 | `view(player)` 的 `pokemon.effective` | `maxHp`、`currentHp`、有效弱点／抗性、撤退费用、能量要求／提供量、特性存在及道具效果可用性 | 根据基础数据和当前有效效果计算，不作为存档权威值 |

例如卡面 HP 100、增加最大 HP 50 的效果、已有 3 个伤害指示物：

```text
definition.mechanics.hp = 100      // 不可变卡面值
pokemon.counters = 3              // 保存的受伤事实
view.effective.maxHp = 150        // 基础值 + 当前适用修正
view.effective.currentHp = 120    // max(0, maxHp - counters × 10)
```

移除增 HP 效果后，指示物仍为 3 个，剩余 HP 成为 70；
回复移除指示物，不改卡面 HP。进化后使用新最上层卡的基础值，
而不是将旧剩余 HP 当成新卡的基础属性。同一定义的多张实例互不共享受伤状态。
`CardDefinition` 不接受 `currentHp`、伤害和临时封锁；运行时宝可梦也
不接受 `hp`、`maxHp`、卡面属性和招式副本。`facts` 仅允许明确的事件记录，
不能把这些属性藏进一个任意键值包。

“下个自己的回合不能使用这项招式”使用独立 `restriction` 载荷：
目标为固定 `pokemonId`，保存来源及可选的 `attackIds`，
时间为 `nextOwnTurn` 和明确的持有者回合／到期边界，
另明确回到备战区或进化时是否清除。没有通用的
`cannotUseSkillNextTurn: true`，也不永久删除卡面招式。
**招式使用限制、特性发动限制和特殊状态不是同一机制**；
`restriction.actions` 只包括 `attack`／`retreat`；
特性消除走独立的有效来源推导，不能与这两个动作封锁互相代替。

### CardPrinting

规范：`schemas/card-printing.schema.json`。

- 发行语言和完整卡号原样保存；单一 Wiki 页面不是单一规则版本。
- `definitionBindings[]` 明确关联地区／版本和对应定义；歧义立即拒绝。
- 保留 Pocket 或其他语言资料用于归档，不意味着可以进入简中实体 TCG 对战。
- 同名重印的赛制适用性与规则说明更新应由独立赛制清单审核，
  不能只看卡牌所属系列或只看旧印刷的标记。
- 第十五轮接通标准／开放固定卡池，新增静态 `series`／`releasedOn`／`formatReviews`，
  审批与封签覆盖这些元数据；旧卡必须绑定最新版定义及经审核的最新印刷。
  创建和恢复都执行卡池检查，赛制不混入卡牌 HP、伤害或回合状态；
  详见 `FORMATS.md`，不代表真实生产卡池或所有特殊卡机制已验收。

生成的验证器在 `public/rules/schema-validators.js`；用
`npm run rules:build` 同时重建验证器与内核构建指纹；
`npm run rules:schema:check`／`npm run rules:kernel:check` 防止陈旧。
验证器在浏览器与 Node 中离线运行，无运行时 schema 编译或 `eval`。

### 独立印刷审批与发布目录

规则定义和印刷身份分别作完整内容绑定审批。印刷中的 `verified` 标记不再
能单独进入执行目录，编号、语言、标记、定义绑定和来源被改动时旧审批失效。
未信任数据可通过 `catalog-release.schema.json` 与独立安装的 manifest 哈希名单接入；
其自身的审核声明、内容摘要或自带名单不能签发权限。
内核／schema／规则来源及安装的 handler 合约都参与发布与目录身份，
已批准目录对象的回执与普通开发目录分开。完整流程与信任边界见 `RELEASE.md`。
这些是软件准入约束，不伪称为简中赛场规则要求 SHA-256，也不代表实际卡池已获批准。

## 5. 迁移策略

先保留旧教学模式，不把现有 1,270 个定义批量标记为简中合规。
新增明确版本的引擎入口和迁移审查报告；未通过的卡牌仍只能用于旧模式或展示。
不能为了兼容旧测试而在官方模式保留冲突行为。

不要求复制所有卡牌脚本才能完成核心规则设计，但每个宣称可用的卡牌／handler
都必须完整实现对应效果；“所有卡牌自动可玩”不属于可以推断出的能力。
新内核接入前网站仍使用旧实现，不能提前显示“已按 V20261019 结算”。

## 6. 验收测试设计

1. 来源与版本：章节可定位、规则有来源、不接受未知地区或 `latest`、
   更新源文件不改旧快照、卡牌审批变更失效。
2. Schema：三种卡牌正反例、完整卡号、印刷绑定、未知属性、未知 handler、
   错误参数、缺值、未实现状态、不同地区和 Pocket 拒绝。
3. 纯规则：各伤害阶段及提前终止、同阶段叠加、特殊属性组合、
   备战／自身／指示物差异、能量支付的独立穷举 oracle、
   选择数量及隐藏区域例外。
4. 状态机：双方共同重抽和净补牌、补牌与奖赏顺序、先后攻选择、
   首回合特例、进化和退化、撤退支付、训练家限制、主动认输。
5. 交互：顺序、费用、然后、选择受保护目标、反击、连续能力消除、
   最后已知信息、同时昏厥、简中胜负表及一奖赏抢分赛。
6. 不变量／重放：60 张守恒、卡牌唯一归属、隐藏信息投影、
   无效命令原子拒绝、随机数可重复、每个选择点恢复、实例隔离、
   两场同时运行的游戏不得互相影响。
7. 集成：新模式入口、默认／旧模式标签、存档版本迁移、网页构建、
   UI 与 AI 同路径、已审批牌组可完成对局。

测试必须对照官方例子和独立预期，不能只调用同一个实现计算预期。
通过多少个测试不是“完备”的证明；所有待实现条款和交互仍要列明并关闭。
